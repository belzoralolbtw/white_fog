# ROADMAP_STEPS.md — ## Суть мода

Постоянная ночь. Свет снижает воздействие тьмы, погасшее освещение делает вылазку опасной. Игрок находит обсерваторию, активирует четыре фонарных поста, связывает их с главным маяком и выдерживает финальное испытание. Посты — обычные фонари, главный маяк — один vanilla beacon. Новые наборы одежды, металлургия, мокрота, транспорт и новые мобы в этот вариант не входят.


Каждый тикет является автономным. Кодеру передаётся только один выбранный тикет. Внутри тикета повторены все значения, рецепты, ID и проверки, необходимые для его реализации.

## Обязательный технический контракт версии

- Единственная целевая версия: **Minecraft 26.2**, Fabric Loader/API для 26.2. Stonecutter, версии 26.1.2 и 26.3, NeoForge и Forge не используются.
- Использовать деобфусцированные имена Minecraft 26.2. Не добавлять mappings line, предназначенную для обфусцированных версий.
- Common-код не импортирует `net.minecraft.client.*`. Клиентские классы находятся только в client source set/initializer.
- Для идентификаторов использовать `net.minecraft.resources.Identifier`, для векторов `net.minecraft.world.phys.Vec3`, для типов сущностей — API Minecraft 26.2 (`net.minecraft.world.entity.EntityTypes` там, где требуется тип сущности).
- Для C2S/S2C регистрировать custom payload type один раз в common initializer до регистрации receiver: `PayloadTypeRegistry.serverboundPlay()` для C2S и `PayloadTypeRegistry.clientboundPlay()` для S2C. Регистрация receiver без предварительно зарегистрированного payload запрещена.
- Для HUD использовать client API Minecraft 26.2 с Fabric `HudElementRegistry`/`HudElement`; common gameplay code не должен ссылаться на `GuiGraphicsExtractor`.
- Для клавиш не использовать `org.lwjgl.glfw.GLFW`; использовать `com.mojang.blaze3d.platform.InputConstants`.
- Для сохранения использовать серверный persistent state или компонент игрока с сериализацией в NBT/Codec; состояние обязано переживать save/load, unload/load чанка, disconnect/reconnect.
- Все проверки ресурсов, таймеров, дистанций, урона, крафта и движения выполняются на сервере. Клиентский GUI только отображает состояние и отправляет запрос действия.
- `1 игровой день = 24000 тиков`, `20 тиков = 1 секунда`. Если требуется реальное время, значение указывается отдельно; игровые длительности не смешивать с реальными.
- Любой длительный процесс хранит `startedAt`, `lastProcessedAt`, `duration`, `state`, входы и выход. При загрузке обрабатывать только интервал между фактическими игровыми timestamp.
- Любое списание ресурсов выполняется атомарно после серверной проверки всех входов. Нельзя списывать часть рецепта до подтверждения возможности завершить действие.
- Для каждого изменения использовать проверку сборки и запуск целевого Gradle-задачи для 26.2; кодер не должен добавлять API из других версий Minecraft.


## Этап 1.7: Закрытое укрытие и адаптер света

### Контекст и границы

- Minecraft 26.2, Fabric Loader0.19.5/API0.161.0+26.2, Java25+, Loom1.18.3, Gradle9.7.1, `white_fog`. Готовые1.1–1.4 не менять, новых items/blocks/entities нет. Использовать существующий единый server tick.
- Exposure-сервис уже принимает DTO `{blockLight,canSeeSky,shelter,alive,exempt,victorySafe}`. Темнота light<=4 даёт+1 за20т, открытое небо вне shelter ещё+1; bright>=9 даёт−2. Здесь заменить только shelter=false adapter реальным detector. Не вводить отдельный «световой радиус», умножающий реальный block light.
- План: `darkness/shelter/{ShelterDetector,ShelterCache,ShelterSnapshot}.java`; чистые тесты на voxel DTO. Нет постоянных мировых shelter entities и структурных HP.

### Данные и интерфейсы

- Вход detector: dimension, feet BlockPos, read-only loaded voxel provider. Выход `{valid:boolean, interiorMin,interiorMax, reason}`. Reasons: VALID/UNLOADED/TOO_LARGE/OPEN_VOLUME/NO_FLOOR/NO_ROOF/INVALID_START/TOO_SMALL.
- Runtime cache на игрока: `{feetPos,dimension,checkedAt,bbox,valid,reason}`. Максимальный срок20т; cache не сериализуется. Базовое player-поле shelterValid — только последняя проекция, не источник истины.
- Проектный интерфейс `ShelterProvider.isSheltered(player)->boolean` подключается в existing exposure tick перед вычислением exposure. При отсутствии загруженного объёма возвращается false, не устаревшее true.
- Константы: шесть face-соседей, максимум125 interior cells **включительно**, bbox максимум9×5×9, минимум18 клеток (=3×2×3), cache20т. Порядок обхода DOWN,UP,NORTH,SOUTH,WEST,EAST фиксирован.

### Правила и алгоритм

1. Укрытие — замкнутая комната. **Открытая дверь не считается стеной**: это однозначное правило для BFS, без исключения «разрешённый открытый вход». Закрытая vanilla дверь и закрытый trapdoor являются преградой через свою плоскость, если их state/shape реально перекрывает проверяемый проход; тонкая декорация не заменяет стену.
2. Исходная feet-клетка должна быть loaded, без жидкости, позволять игроку стоять. Полная solid-клетка как start→INVALID_START. Блоки с непустой частичной collision, не относящиеся к закрытой двери/trapdoor, считаются проходимыми для поиска утечек: fence/slab не герметичная стена.
3. BFS читает соседние клетки. Full solid faces сдерживают проход; закрытая дверь сдерживает переход через своё полотно, а не все шесть направлений. Для тестового voxel provider это явная маска blockedFaces. Для реального адаптера mask получается из проверенных collision/state API, не из названий блоков.
4. Добавление126-й клетки→TOO_LARGE. Выход bbox ширины>9,высоты>5,глубины>9 тоже false. Если требуется прочитать unloaded cell, UNLOADED. Никакого chunk load ради detector.
5. После завершённого BFS проверка floor/roof для каждой занятой XZ-колонки: solid верхняя грань непосредственно под минимальным interiorY и solid нижняя грань над максимальным interiorY. Вода, открытый trapdoor, slab без соответствующей полной грани не годятся. Внутренние air-клетки не обязаны каждая иметь пол/потолок: проверяются концы колонок.
6. Минимум18 найденных клеток, хотя бы один свободный столбик высоты2; иначе TOO_SMALL. Закрытая комната без двери допустима. Количество закрытых дверей не ограничивать: все герметичные границы равнозначны.
7. On player feet/dimension change пересчитать до sample. Любое изменение block state в cache bbox+1 инвалидирует cache; стационарный игрок также получает проверку каждые20т. Один блок крыши, открывший наружный объём, обнаруживается тем же алгоритмом, без отдельного счётчика «две стены».
8. Shelter не создаёт свет, не лечит автоматически и не запрещает мобу зайти в открытый вход. Правила exposure остаются server block light based. Vanilla bed не перематывает зафиксированную ночь; отдельного сна или восстановления усталости этот этап не создаёт.

### Сбои и сохранение

- На unload/reconnect/dimension cache уничтожается; первый sample требует нового чтения. Нельзя хранить true из другого измерения/комнаты.
- Ни предметы, ни блоки, ни ресурсы detector не изменяет. Ошибка чтения окружения→false и dev-log с координатами, не краш всего server tick.
- Два игрока при одинаковых feet/voxel DTO получают одинаковый результат независимо от порядка tick. После их движения cache допускает разные результаты по разным комнатам.

- Sandbox `tests/eternal_darkness/shelter/`: interior3×2×3 с solid оболочкой true; закрытая дверь true; открытая false; крыша с одной дырой false; вода в start false; floor hole false; слэбовая щель false;125/126клеток, bbox9/10, unloaded face, пустой cache после dimension.
- Проверить правильную маску дверного полотна на всех4facing и обеих halves; roof/floor по колонкам, а не невозможный floor для каждой air-клетки.
- Runtime: вырезанная пещерная комната, построенный дом, неподвижный игрок при открытии двери другим игроком, chunk boundary, двое. Exposure под крышей без света всё ещё растёт+1/sample; lantern меняет block light, не shelter truth.
- Сначала sandbox/raw UTF-8 logs с timing, после разрешения main и референса/26.2 API lookup build `--no-daemon --console=plain`, bounded server/client smoke180с, внешний timeout больше; новый лог и `status=SUCCESS|FAILURE|TIMEOUT`. Сам detector тестируется как read-only; headless startup не доказательство реальной collision geometry.
